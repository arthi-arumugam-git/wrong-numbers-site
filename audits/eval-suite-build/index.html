( Who it's for )

Who this
is for.

For teams shipping an LLM feature without evals they trust, or measuring it with a public benchmark that doesn't reflect what their users actually do.

Most eval suites are built to produce a number. This one is built so the number can't be wrong quietly: every metric says how much it measured, every judge fails closed when its answer can't be parsed, and every empty case raises instead of scoring.

( What I check )

Six places
the number goes wrong.

  1. 01

    Ground-truth data and rubrics

    A dataset drawn from your real inputs, with the expected behaviour written down, and rubrics that a person and a judge can both apply.

  2. 02

    Judges that fail closed

    LLM-as-judge prompts and parsers that read the verdict, not the rubric, and count a rating that doesn't parse as a failure rather than a score.

  3. 03

    Metrics that report nan

    Metrics that report nan or raise when nothing was measured, and say how many samples each number covers.

  4. 04

    On your stack

    Built on inspect_evals, lm-evaluation-harness, TruLens or plain Python and pytest, whichever fits the repository you already have.

  5. 05

    A baseline with its noise

    A first run with a noise check, so you know how much a score moves when nothing has changed before you read meaning into a difference.

  6. 06

    Wired into CI

    The suite runs in CI with thresholds that fail the build, so a regression is caught on the pull request that caused it.

( How it runs )

  1. 01

    Reproduce

    Hold the model, prompts and tool schemas constant, and rerun until every number is accounted for, against a known-answer test or your provider's invoice.

  2. 02

    Measure

    A baseline noise check first, then the real numbers, with the limits of the measurement written down.

  3. 03

    Fix

    A pull request for each finding, with a test that fails on the old behaviour and passes on the new.

  4. 04

    Gate

    Checks wired into CI, so the next wrong number fails the build instead of reaching a decision or an invoice.

( Questions )

Eval suite build,
answered.

What is included in an eval suite build?

Ground-truth data and rubrics from your real inputs, LLM judges whose parsing fails closed, metrics that report nan when nothing was measured, a baseline run with its noise measured, and CI wiring that fails the build on a regression.

Which eval framework will it use?

Whichever fits your repository: inspect_evals, lm-evaluation-harness, TruLens, or plain Python with pytest. The design rules are the same in each.

How is this different from the eval integrity audit?

The audit checks a suite you already run. The build creates one, or replaces one you don't trust, designed from the start so its numbers fail loudly.
