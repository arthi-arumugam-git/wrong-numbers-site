( Who it's for )

Who this
is for.

For teams running LLM agents in production, where a prompt change, a model upgrade or a library bump can drop a tool call, change its arguments or double its cost while every test still passes.

The gates compare each run with a known-good one, step by step, and fail the build on the differences you decide matter. They are built on whatbroke, my open-source agent run-diffing CLI.

( What I check )

Five places
the number goes wrong.

  1. 01

    Run diffs, step by step

    Two runs compared by tool calls, arguments, outputs, latency and cost, so a missing or changed step shows up as a diff.

  2. 02

    Your traces, as they are

    Imports from JSONL, OpenTelemetry, Langfuse and LangSmith exports, so the gates read the traces you already collect.

  3. 03

    Failure gates you choose

    A GitHub Action that breaks CI on the conditions you set: a tool call lost, an argument changed, cost or latency over a threshold.

  4. 04

    Streamed and non-streamed parity

    The same request should produce the same tool calls with and without streaming; a streaming parser can quietly turn a tool call into plain text.

  5. 05

    Usage that survives the stream

    Token usage accumulated across a stream should not be overwritten by the final event, or every streamed run under-reports its cost.

( Questions )

Agent regression gates,
answered.

What is an agent regression gate?

A CI check that compares a new agent run with a known-good one and fails the build when the difference crosses a line you set: a tool call that disappeared, an argument that changed, a cost that jumped.

Which tracing formats can the gates read?

JSONL, OpenTelemetry, Langfuse and LangSmith exports, through whatbroke's importers.

Do I need to change how my agent is built?

No. The gates work from the traces your agent already produces, so the agent code stays as it is.
